# Данные: профиль и правила обработки

Файлы: `data/raw/turbine_1.csv`, `data/raw/turbine_2.csv` (переименованы из выданных организаторами,
профилированы 23.09.2026).

## Структура

| Колонка | Описание |
| --- | --- |
| `ID` | порядковый номер строки |
| `Статистическое время` | локальное время, шаг 10 минут, формат `YYYY-MM-DD H:MM:SS` |
| `Средняя скорость ветра(m/s)` | измеренная на турбине |
| `Нормализованная активная мощность` | **целевая переменная**, 0–1 |
| `Средняя температура окружающей среды(°C)` | измеренная на турбине |

Диапазон: **2023-03-11 00:00 → 2026-01-31 23:50**, обе турбины.

## Правила обработки (обязательны для всех)

1. **Агрегация к часу:** прогноз почасовой → target = среднее нормализованной мощности за час.
   Час засчитываем, только если в нём ≥ 4 из 6 десятиминуток (иначе target = NaN, строка не идёт в обучение).
2. **Пропуски НЕ интерполируем в target.** Причина пропуска по этим данным не установлена.
   Интерполяция мощности внесёт фиктивные значения в обучение.
3. **Время хранится без UTC offset и трактуется как локальное Asia/Almaty.** Open-Meteo
   запрашивается с этой зоной; историческую стыковку проверяем по датам.
   Все склейки данных — через явный `timezone="Asia/Almaty"` в запросах к API. Ошибка на 5 часов
   в склейке погоды с мощностью — худший тихий баг этого кейса, проверяется тестом на корреляцию
   прогнозного и измеренного ветра (сдвиг с максимумом корреляции должен быть 0).
4. **Предполагаемый простой:** для каждого 10-минутного отсчёта проверяется мощность <0.02
   при ветре >4 м/с. Если таких отсчётов ≥50% за час, его target исключается из обучения.
   Проверки непрерывности простоя нет. Это эвристика: отсутствие мощности может иметь
   разные причины, поэтому в оценке нужно отдельно показывать все наблюдаемые часы.
5. **Измеренные на турбине ветер и температура доступны только в истории.** На инференсе их нет —
   входом служит **прогноз погоды**. Поэтому обучаемся на прогнозных фичах (см. RESEARCH.md),
   измеренные значения используем только для контроля качества источника погоды.
6. После агрегации остаются десятки тысяч часов, затем применяются ограничения погодного
   архива и фильтры target. Точное число обучающих строк зависит от периода и представления
   горизонтов. Сравнение с нейросетями требует отдельного эксперимента (ADR-002).

## Происхождение обучающих и оценочных строк

`issued_feature_stack()` строит признаки отдельно для каждого среза выпуска тем же путём,
что ежедневный прогноз. `training_matrix()` сохраняет только известные цели с погодным
входом и применяет явную верхнюю границу: 31.01.2026 для подачи, 30.11.2025 для оценочных
моделей. Лаги и окна остаются внутри среза; происхождение содержит `issue_date`, `datetime`
и `lead_day`. Точность стыковки признаков проверяют `tests/test_feature_availability.py`.

Оценочный CSV хранит исходную часовую мощность и отдельный `target_eligible`, чтобы
сравнивать чистые цели и все наблюдаемые часы без заполнения пропусков. Границы и полнота
оценки — [EVALUATION](EVALUATION.md), результаты — `models_artifacts/evaluation/`.
Равенство признаков не доказывает доступность NWP к часу публикации: ограничение кэша
и покрытие архивов конкретных прогонов описаны в [FEATURE_AVAILABILITY](FEATURE_AVAILABILITY.md).
