# Репетиция релиза: одна команда, Linux CI и контейнер без сети

Что проверяет `scripts/reproduce.py`, почему образ не обучает модели, что делает CI,
какие проверки выполнены на самом деле и как обеспечивается переносимость признаков
между macOS и Linux.
Основание: [CASE](CASE.md), [JUDGE_GUIDE](JUDGE_GUIDE.md), [EVALUATION](EVALUATION.md),
[INTEGRATION](INTEGRATION.md).

## 1. Одна команда

```bash
python -m scripts.reproduce --output-dir runs/reproduction
```

Работает без сети, без ключей и без обучения, используя сохранённые модели
`models_artifacts/` и кэш `data/weather_cache/`. Порядок проверок и условия отказа:

| Проверка | Что делается | Отказ |
| --- | --- | --- |
| каталог результатов | `--output-dir` приводится к realpath; отклоняются корень репозитория, `data/`, `models_artifacts/`, `forecasts/`, `src/`, `tests/`, `scripts/`, `docs/`, `.git/`, `.github/` и любой путь внутри них, в том числе через symlink; непустой каталог отклоняется без очистки | код 2, ничего не пишется |
| `manifest` | SHA256 всех файлов `data/raw`, `data/weather_cache`, `models_artifacts`, `forecasts` сверяются с непустыми `input_sha256`/`output_sha256` из `models_artifacts/manifest.json`; собственный хэш манифеста исключён, хэши исходников не сверяются | неверный формат манифеста; отсутствующий, изменённый или не включённый в манифест файл комплекта |
| `weather_cache` | до прогона проверяется наличие каждого файла кэша, нужного `get_weather`; сеть в процессе уже заблокирована (`httpx.get/post/request`, `httpx.Client.send`, `socket.connect`, `socket.create_connection`) | недостающий кэш; прогон не начинается |
| `forecast_runs` | 28 выпусков 31.01–27.02.2026 через `run_day_no_llm` сохранёнными моделями; сводная подача — в output-dir | незавершённый выпуск, ошибка графа, число выпусков ≠ 28 |
| `submission` | `scripts.verify_submission` за 1–28 февраля и подсчёт 1344 turbine-hours | ошибка верификатора или другое число строк |
| `forecast_match` | подача и все 56 дневных CSV сравниваются с `forecasts/` по каждому числовому столбцу; фиксируются максимальное абсолютное отклонение и число строк, совпавших точнее `1e-9` | отклонение больше `--tolerance`, иной набор часов или столбцов |
| `evaluation_metrics` | `compute_metrics` пересчитывает метрики из `models_artifacts/evaluation/evaluation_predictions.csv` и сравнивает с `evaluation_report.json`: целые точно, вещественные с допуском `1e-9` **независимо от `--tolerance`**; `coverage.actual_rows` = число строк CSV | любое расхождение или отсутствующий ключ |
| `evaluation_replay` | сохранённые оценочные модели `models_artifacts/evaluation/turbine_*.pkl` заново предсказывают оценочный период (62 выпуска), результат сравнивается с CSV по уникальным ключам и значениям; обучение не выполняется | дубли или несовпадение ключей, разное число строк, пропущенный выпуск, отклонение больше `--tolerance` |
| `canonical_unchanged` | повторный SHA256 всех канонических файлов | изменённый, удалённый или добавленный файл |

`reproduction_report.json` пишется только в output-dir: платформа, версии, commit,
диапазон выпусков, допуск, результат и длительность каждой проверки, максимальные отклонения
и число точно совпавших строк. Код выхода: 0 — все проверки прошли, 1 — есть отказ,
2 — неверные параметры или каталог. `--skip-evaluation-replay` пропускает только воспроизведение
оценочных прогнозов; пересчёт метрик из CSV выполняется всегда.

Репетиция проверяет полное релизное окно: `--start 2026-01-31 --end 2026-02-27`.
Частичный диапазон отклоняется до создания каталога: каноническая подача содержит весь
февраль. Допуск должен быть конечным неотрицательным числом; `NaN` и бесконечность запрещены.

Допуск по умолчанию `1e-9` используется и локально, и в Docker, и в CI. Число строк,
отличающихся сильнее `1e-9`, остаётся в отчёте и сводке. Для диагностического сравнения
можно указать другой `--tolerance`, но релизные проверки его не увеличивают. Метрики
из сохранённого CSV всегда сверяются с `1e-9` независимо от этого параметра.

### Чего команда не доказывает

- Точность февраля: факта у команды нет, сравнение идёт с сохранёнными числами команды.
- Доступность погоды к часу выпуска: ограничение архива описано в
  [FEATURE_AVAILABILITY](FEATURE_AVAILABILITY.md).
- Работу LLM: репетиция выполняется в режиме без LLM; живой вызов — отдельная проверка
  владельца ключа ([JUDGE_GUIDE §4](JUDGE_GUIDE.md)).
- Переобучаемость: `python -m src.cli train` и `python -m src.backtest.evaluate` намеренно
  не вызываются, чтобы репетиция не подменила проверенные артефакты другими.

## 2. Docker: проверенный комплект без обучения при сборке

Раньше `Dockerfile` обучал модели при `docker build`, а `.dockerignore` исключал
`models_artifacts/`. Такой образ показывал бы не те числа, которые интегратор проверил
и записал в `manifest.json`, и оставлял панель без сохранённой оценки. Теперь:

- в образ входят код, `data/`, `models_artifacts/` (включая `evaluation/`) и `forecasts/`;
  исключены `.git`, `.github`, `.env*` (кроме `.env.example`), IDE-каталоги, `.venv`/`venv`,
  `runs/`, кэши тестов и байткод, `docs/img`;
- обучения при сборке нет; вместо него проверка комплекта без сети: сохранённые модели
  читаются установленным scikit-learn; `warnings.simplefilter` превращает
  `InconsistentVersionWarning` в ошибку после импорта класса предупреждения, а
  `scripts.verify_submission` подтверждает целостность канонической подачи;
- база `python:3.12-slim` плюс `libgomp1` для LightGBM; телеметрия Streamlit отключена,
  чтобы панель не пыталась выйти в сеть; `HEALTHCHECK` опрашивает `/_stcore/health`.

Команды:

```bash
docker compose up --build                 # панель на http://localhost:8501
docker compose run --rm reproduce         # offline-репетиция, network_mode: none, допуск 1e-9
docker run --rm --network none windcast:latest \
  python -m scripts.reproduce --output-dir /tmp/reproduction
```

Сервис `windcast` монтирует `./forecasts` только для чтения: панель видит канонические
файлы хоста, но контейнер не может их изменить. Сервис `reproduce` (профиль `check`)
пишет в `./runs/reproduction-docker`; каталог должен быть пустым или отсутствовать.
Переобучение в контейнере возможно только явной командой `python -m src.cli train`
и заменяет артефакты внутри этого контейнера.

## 3. GitHub Actions: `.github/workflows/reproducibility.yml`

Запускается на push в `main` и `dev/**`, на pull request и вручную. Ключей не требует,
результаты не коммитит; отчёт репетиции сохраняется как артефакт задания.

| Задание | Шаги |
| --- | --- |
| `linux` (ubuntu-24.04, Python 3.12, pip-кэш) | установка закреплённых `requirements.txt`; полный `pytest -q -rs`, при любом `skipped` — ошибка (Streamlit-тесты обязаны выполняться); `scripts.verify_submission`; `scripts.reproduce --output-dir runs/reproduction`; вывод числа строк в пределах `1e-9` |
| `docker` (ubuntu-24.04) | `docker build`; `docker run --rm --network none … scripts.reproduce` с допуском по умолчанию `1e-9`; запуск панели, ожидание `/_stcore/health`, HTTP-код главной страницы, статус healthcheck |

Обучение в CI не выполняется и не дублируется: оба задания используют сохранённый комплект.
HTTP 200 панели не заменяет `AppTest`: оба режима UI проверяют существующие тесты в задании
`linux`. Ссылка: `https://github.com/BAITC-Hacks/hack-f0ab74e4-knewit-3/actions/workflows/reproducibility.yml`.

**Состояние на 23.09.2026.** Первый запуск на ветке `dev/release-rehearsal`
(run 35854882460, коммит `10b8e14`) завершился за 4 с без единого шага и без раннера;
аннотация GitHub: «The job was not started because your account is locked due to a billing
issue». Это блокер на стороне организации `BAITC-Hacks` (hosted-раннеры для приватного
репозитория). GitHub API подтверждает отсутствие выделенного раннера и ноль выполненных
шагов: этот запуск не проверил код. Пока биллинг не разблокирован, CI-подтверждения нет.
Локальные Linux-проверки фиксируются отдельно в разделе 5. После разблокировки достаточно
повторно запустить workflow вручную (`workflow_dispatch`) или сделать любой push в ветку.

## 5. Проверка пересобранного комплекта на Linux

Финальный строгий прогон на Linux пока не подтверждён. Для приёмки требуется образ
с теми же сохранёнными моделями, прогнозами, оценкой и манифестом, что проверены на macOS:

```bash
docker build -t windcast:rehearsal .
docker run --rm --network none windcast:rehearsal python -m pytest tests/ -q -rs
docker run --rm --network none windcast:rehearsal \
  python -m scripts.reproduce --output-dir /tmp/reproduction
```

Отчёт должен показать все восемь проверок `OK`, 1344 строки подачи и 5904 строки оценки,
нулевое число строк за порогом `1e-9` и неизменность канонических файлов. В итоговых
результатах указываются версия Python, архитектура Linux, версии пакетов, максимальные
отклонения и отсутствие сети у контейнера. Готовность панели проверяется отдельно через
`/_stcore/health` и тесты `AppTest`.

## 6. Переносимость признаков и пересборка моделей

В исходном комплекте вычисления `sin`, `cos` и степеней на macOS и Linux различались
в младших битах float64. LightGBM мог поставить порог между математически равными
значениями `hour_cos`, например для 11 и 13 часов. Изменение входа на один шаг float64
тогда выбирало другой лист дерева. В исходной репетиции это затронуло 52 из 1344 часов
подачи; максимальное отклонение среди прогнозных столбцов достигало `2.65e-2`.

Исправление задаёт общую числовую точность на границе `build_features`: вся готовая
матрица признаков округляется один раз до 10 знаков после запятой. Это одинаковая
обработка для обучения, февральского прогноза и ретроспективной оценки. Округление
готовой матрицы охватывает и производные признаки, а пропуски сохраняются для LightGBM.
Регрессионные тесты проверяют симметричные часы и возмущения соседними значениями
float64 через `nextafter`, имитирующие различия математических библиотек.

Обновление признаков требует переобучить канонические и оценочные модели, затем заново
сформировать февральские прогнозы, оценочный CSV, отчёт с метриками и `manifest.json`.
Пороги старых деревьев обучены на прежних значениях: замена только инференса не создаёт
согласованный комплект. При пересборке сохраняются прежние отсечки данных и протокол
оценки; прогнозы и метрики относятся уже к новым моделям.

Из `docker-compose.yml` и GitHub Actions удалён прежний увеличенный допуск `0.05`.
Приёмка пересобранного комплекта требует строгого `1e-9` на обеих платформах. Само
округление не является доказательством для всех ОС и архитектур: выполненные прогоны
и их параметры фиксируются в разделах 4–5 после проверки.
