# Репетиция релиза: одна команда, Linux CI и контейнер без сети

Что проверяет `scripts/reproduce.py`, почему образ не обучает модели, что делает CI,
какие проверки выполнены на самом деле и откуда берётся расхождение между macOS и Linux.
Основание: [CASE](CASE.md), [JUDGE_GUIDE](JUDGE_GUIDE.md), [EVALUATION](EVALUATION.md),
[INTEGRATION](INTEGRATION.md).

## 1. Одна команда

```bash
python -m scripts.reproduce --output-dir runs/reproduction
```

Работает без сети, без ключей и без обучения, используя сохранённые модели
`models_artifacts/` и кэш `data/weather_cache/`. Порядок проверок и условия отказа:

| Проверка | Что делается | Отказ |
| --- | --- | --- |
| каталог результатов | `--output-dir` приводится к realpath; отклоняются корень репозитория, `data/`, `models_artifacts/`, `forecasts/`, `src/`, `tests/`, `scripts/`, `docs/`, `.git/`, `.github/` и любой путь внутри них, в том числе через symlink; непустой каталог отклоняется без очистки | код 2, ничего не пишется |
| `manifest` | SHA256 всех файлов `data/raw`, `data/weather_cache`, `models_artifacts`, `forecasts` сверяются с `input_sha256`/`output_sha256` из `models_artifacts/manifest.json`; хэши исходников не сверяются, потому что код репетиции меняется законно | отсутствующий или изменённый файл комплекта |
| `weather_cache` | до прогона проверяется наличие каждого файла кэша, нужного `get_weather`; сеть в процессе уже заблокирована (`httpx.get/post/request`, `httpx.Client.send`, `socket.connect`, `socket.create_connection`) | недостающий кэш; прогон не начинается |
| `forecast_runs` | 28 выпусков 31.01–27.02.2026 через `run_day_no_llm` сохранёнными моделями; сводная подача — в output-dir | незавершённый выпуск, ошибка графа, число выпусков ≠ 28 |
| `submission` | `scripts.verify_submission` за 1–28 февраля и подсчёт 1344 turbine-hours | ошибка верификатора или другое число строк |
| `forecast_match` | подача и все 56 дневных CSV сравниваются с `forecasts/` по каждому числовому столбцу; фиксируются максимальное абсолютное отклонение и число строк, совпавших точнее `1e-9` | отклонение больше `--tolerance`, иной набор часов или столбцов |
| `evaluation_metrics` | `compute_metrics` пересчитывает метрики из `models_artifacts/evaluation/evaluation_predictions.csv` и сравнивает с `evaluation_report.json`: целые точно, вещественные с допуском `1e-9` **независимо от `--tolerance`**; `coverage.actual_rows` = число строк CSV | любое расхождение или отсутствующий ключ |
| `evaluation_replay` | сохранённые оценочные модели `models_artifacts/evaluation/turbine_*.pkl` заново предсказывают оценочный период (62 выпуска), результат сравнивается с CSV по ключам и значениям; обучение не выполняется | несовпадение ключей, пропущенный выпуск, отклонение больше `--tolerance` |
| `canonical_unchanged` | повторный SHA256 всех канонических файлов | изменённый, удалённый или добавленный файл |

`reproduction_report.json` пишется только в output-dir: платформа, версии, commit,
диапазон выпусков, допуск, результат и длительность каждой проверки, максимальные отклонения
и число точно совпавших строк. Код выхода: 0 — все проверки прошли, 1 — есть отказ,
2 — неверный каталог. `--skip-evaluation-replay` пропускает только воспроизведение
оценочных прогнозов; пересчёт метрик из CSV выполняется всегда.

Допуск `--tolerance` по умолчанию `1e-9`: на платформе, где создан комплект (macOS arm64),
прогнозы совпадают побитово, а различия порядка суммирования дают не более `1.1e-16`.
На Linux допуск нужно задавать явно по причине из раздела 6; число строк, совпавших точнее
`1e-9`, всегда остаётся в отчёте и в сводке, чтобы ослабленный допуск не скрывал масштаб
различий. Тест `test_forecast_values_beyond_tolerance…` показывает, что различие `3e-7`
при допуске `1e-9` — отказ, а `--tolerance 1e-6` пропускает его, но записывает 24 неточные строки.

### Чего команда не доказывает

- Точность февраля: факта у команды нет, сравнение идёт с сохранёнными числами команды.
- Доступность погоды к часу выпуска: ограничение архива описано в
  [FEATURE_AVAILABILITY](FEATURE_AVAILABILITY.md).
- Работу LLM: репетиция выполняется в режиме без LLM; живой вызов — отдельная проверка
  владельца ключа ([JUDGE_GUIDE §4](JUDGE_GUIDE.md)).
- Переобучаемость: `python -m src.cli train` и `python -m src.backtest.evaluate` намеренно
  не вызываются, чтобы репетиция не подменила проверенные артефакты другими.

## 2. Docker: проверенный комплект без обучения при сборке

Раньше `Dockerfile` обучал модели при `docker build`, а `.dockerignore` исключал
`models_artifacts/`. Такой образ показывал бы не те числа, которые интегратор проверил
и записал в `manifest.json`, и оставлял панель без сохранённой оценки. Теперь:

- в образ входят код, `data/`, `models_artifacts/` (включая `evaluation/`) и `forecasts/`;
  исключены `.git`, `.github`, `.env*` (кроме `.env.example`), IDE-каталоги, `.venv`/`venv`,
  `runs/`, кэши тестов и байткод, `docs/img`;
- обучения при сборке нет; вместо него проверка комплекта без сети: сохранённые модели
  читаются установленным scikit-learn без `InconsistentVersionWarning`, а
  `scripts.verify_submission` подтверждает целостность канонической подачи;
- база `python:3.12-slim` плюс `libgomp1` для LightGBM; телеметрия Streamlit отключена,
  чтобы панель не пыталась выйти в сеть; `HEALTHCHECK` опрашивает `/_stcore/health`.

Команды:

```bash
docker compose up --build                 # панель на http://localhost:8501
docker compose run --rm reproduce         # offline-репетиция, network_mode: none, --tolerance 0.05
docker run --rm --network none windcast:latest \
  python -m scripts.reproduce --output-dir /tmp/reproduction --tolerance 0.05
```

Сервис `windcast` монтирует `./forecasts` только для чтения: панель видит канонические
файлы хоста, но контейнер не может их изменить. Сервис `reproduce` (профиль `check`)
пишет в `./runs/reproduction-docker`; каталог должен быть пустым или отсутствовать.
Допуск `0.05` в контейнере задан явно и объяснён в разделе 6. Переобучение в контейнере
возможно только явной командой `python -m src.cli train` и заменяет артефакты внутри
этого контейнера.

## 3. GitHub Actions: `.github/workflows/reproducibility.yml`

Запускается на push в `main` и `dev/**`, на pull request и вручную. Ключей не требует,
результаты не коммитит; отчёт репетиции сохраняется как артефакт задания.

| Задание | Шаги |
| --- | --- |
| `linux` (ubuntu-24.04, Python 3.12, pip-кэш) | установка закреплённых `requirements.txt`; полный `pytest -q -rs`, при любом `skipped` — ошибка (Streamlit-тесты обязаны выполняться); `scripts.verify_submission`; `scripts.reproduce --output-dir runs/reproduction --tolerance 0.05`; вывод числа точно совпавших строк |
| `docker` (ubuntu-24.04) | `docker build`; `docker run --rm --network none … scripts.reproduce --tolerance 0.05`; запуск панели, ожидание `/_stcore/health`, HTTP-код главной страницы, статус healthcheck |

Обучение в CI не выполняется и не дублируется: оба задания используют сохранённый комплект.
HTTP 200 панели не заменяет `AppTest`: оба режима UI проверяют существующие тесты в задании
`linux`. Ссылка: `https://github.com/BAITC-Hacks/hack-f0ab74e4-knewit-3/actions/workflows/reproducibility.yml`.

**Состояние на 23.09.2026.** Первый запуск на ветке `dev/release-rehearsal`
(run 35854882460, коммит `10b8e14`) завершился за 4 с без единого шага и без раннера;
аннотация GitHub: «The job was not started because your account is locked due to a billing
issue». Это блокер на стороне организации `BAITC-Hacks` (hosted-раннеры для приватного
репозитория), а не ошибка workflow: файл проверен `actionlint` без замечаний, все `run`-блоки
проходят `bash -n`. Пока биллинг не разблокирован, CI-подтверждения нет; его заменяют локальные
Linux-проверки из раздела 5, выполненные теми же командами. После разблокировки достаточно
повторно запустить workflow вручную (`workflow_dispatch`) или сделать любой push в ветку.

## 6. Расхождение macOS ↔ Linux: причина, размер, лечение

**Наблюдение.** Один и тот же код, одинаковые версии пакетов, побитово одинаковые кэш погоды
(SHA256 совпал), pickle моделей и пороги изотонической регрессии; `power_baseline` совпадает
точно, а прогноз LightGBM отличается на 52 из 1344 часов подачи (максимум `2.1e-2` по
`power_pred`, `2.65e-2` по `power_p10`) и на 382 из 5904 оценочных строк.

**Причина.** Из 108 признаков 7 отличаются между macOS и glibc на 1 ulp (`≈2e-16`):
`*_wd_sin`/`*_wd_cos` (направление ветра), `hour_cos` и `ens_ws_cube` — это `np.sin`,
`np.cos` и возведение в степень, реализованные разными libm. Само по себе это ничто, но
`hour_cos` принимает 24 значения, среди которых математически равные пары
(например, для 11 и 13 часов) вычисляются с разницей в 1 ulp, и LightGBM при обучении ставит
порог ровно между ними: 4 из 14 порогов по `hour_cos` лежат ближе `1e-9` к реальным
значениям признака. На другой libm такие пороги переключаются, лист меняется, и один из пяти
членов ансамбля или квантильная модель даёт другое значение. Linux x86_64 и aarch64
используют одну glibc и совпадают между собой побитово.

**Проверка гипотезы.** Округление всех признаков до 12 знаков перед предсказанием делает
macOS и Linux побитово одинаковыми (0 из 2640 строк за 28 выпусков отличаются), но
относительно текущих моделей меняет 54% строк, потому что пороги обучены на неокруглённых
значениях. Значит лечение требует переобучения, а не правки только инференса.

**Что сделано здесь.** Допуск по умолчанию остаётся `1e-9`; в контейнере и в CI допуск `0.05`
задан явно с комментарием и ссылкой на этот раздел; метрики оценки сверяются строго при любом
допуске; число строк, совпавших точнее `1e-9`, выводится всегда. `0.05` выбран выше измеренного
максимума `3.14e-2` с запасом, но ниже различий, которые дала бы другая модель или другие признаки.

**Рекомендуемое лечение (владелец признаков/ML, вне владения этой ветки).** В
`src/features/build.py` округлять тригонометрические и степенные признаки
(`wd_sin`, `wd_cos`, `hour_sin`, `hour_cos`, `doy_sin`, `doy_cos`, `ws_cube`, `ens_ws_cube`,
`pwr_density`) до 12 знаков в `build_features`, переобучить канонические и оценочные модели,
заново сформировать февральские CSV, оценку и `manifest.json`, после чего убрать
`--tolerance 0.05` из `docker-compose.yml` и `.github/workflows/reproducibility.yml`: репетиция
должна снова проходить со строгим `1e-9` на любой платформе. До этого честная формулировка для
судей: комплект воспроизводится побитово на macOS arm64 и с точностью до `2.65e-2` на
4% часов на Linux по указанной причине.
