# Протокол оценки: ретроспективное воспроизведение по датам выпуска

Что измеряется, чем это отличается от чисел настройки в `train_report.json`
и как воспроизвести. Протокол: `retrospective-issue-replay-v1`.

## Зачем отдельный протокол

До этого изменения одни и те же даты (декабрь 2025 – январь 2026) выполняли две
несовместимые роли: на них выбирались число деревьев, вес бленда и состав погодных
источников — и на них же публиковалась «оценка качества». Кроме того,
`train_report.json` измерял предварительную одиночную модель, а сдаётся ансамбль
из пяти переобученных моделей, посаженный на данных, включающих эти же даты.
Такое число — производительность на подогнанных данных, а не оценка.

Здесь три роли разведены по времени, и оценивается **ровно та конфигурация,
которая сдаётся** (baseline + бленд + 5 LightGBM + квантили), обученная строго
до оценочных целей и прогнанная продовым путём инференса.

## Хронология

| Роль | Период целевых часов | Что на нём происходит |
| --- | --- | --- |
| fit | 2024-03-01 — 2025-09-30 | посадка модели при подборе |
| tune | 2025-10-01 — 2025-11-30 | ранняя остановка, вес бленда |
| evaluate | 2025-12-01 — 2026-01-31 | воспроизведение по датам выпуска |

Оцениваемый ансамбль сажается на fit+tune (цели по 2025-11-30 включительно,
поле `trained_through`). Каждая цель принадлежит ровно одному интервалу по своему
времени; случайного разбиения нет. Дубли целевого часа (lead 1 и lead 2) по
построению попадают в один интервал.

**Это ретроспективная оценка, а не нетронутый тест.** Декабрь–январь ранее
использовались при отборе погодных источников и решений по архитектуре, поэтому
выбор конфигурации мог оптимистично подстроиться под этот период. Честнее ярлыка
не существует: февральского факта у команды нет, и точность февраля здесь
не изобретается и не заявляется.

## Как формируются оценочные прогнозы

Для каждой даты выпуска D из диапазона 2025-11-29 — 2026-01-30:
`get_issued_forecast(D)` → `build_features` → `predict(..., artifacts_dir=...)` —
тот же путь, что у февральской подачи. Строки за пределами оценочного окна
отбрасываются. Каждый оценочный час получает **две** строки: lead 1 (выпуск D-1)
и lead 2 (выпуск D-2).

**Правило агрегации: агрегации нет.** Строки не усредняются; метрики группируются
по `lead_day`. Пустой или битый срез выпуска попадает в `skipped_issues` отчёта
с причиной — молча ничего не пропускается.

Факт (`power_true`) — среднечасовая наблюдаемая мощность из SCADA; отсутствующие
наблюдения остаются NaN и никогда не заполняются. `target_eligible` — флаг чистой
цели (час не в простое, ≥4/6 десятиминуток, правила `docs/DATA.md`). Метрики
считаются в двух группах: `clean_targets` (сопоставимо с обучением) и
`all_observed` (все наблюдаемые часы — судьи сверяют с фактической выработкой,
включая простои).

## Запуск

```bash
python -m src.backtest.evaluate --output-dir runs/evaluation-v1
```

Пишет только в указанный каталог; канонические `forecasts/`, `models_artifacts/`
и кэш погоды не изменяются; LLM не вызывается; сеть не нужна (кэш в репозитории).
Каталог `runs/` не отслеживается git.

## Контракт выходных файлов

### `evaluation_predictions.csv`

| Колонка | Тип | Описание |
| --- | --- | --- |
| `turbine` | int | 1 или 2 |
| `issue_date` | str `YYYY-MM-DD` | дата выпуска прогноза |
| `datetime` | str `YYYY-MM-DD HH:MM:SS` | целевой час, Asia/Almaty |
| `lead_day` | int | 1 или 2 |
| `power_true` | float, может быть NaN | наблюдаемая мощность; NaN = наблюдения нет |
| `power_pred` | float [0,1] | прогноз оцениваемого ансамбля |
| `power_baseline` | float [0,1] | физический baseline (изотоническая кривая) |
| `power_p10`, `power_p90` | float [0,1], может быть NaN | квантильный диапазон |
| `target_eligible` | bool | час пригоден как чистая цель |
| `trained_through` | str `YYYY-MM-DD` | отсечка обучающих целей у модели этой строки |

### `evaluation_report.json`

Поля верхнего уровня: `schema_version` (int, сейчас 1), `protocol` (str),
`periods` ({fit, tune, evaluate}: [начало, конец]), `trained_through`,
`aggregation_rule`, `issue_range`, `config` (погодные источники, турбины,
подобранные параметры: `n_estimators`, `w_lgb`, число членов ансамбля, размеры
выборок), `model_artifacts` (имена pkl в этом же каталоге — именно они дали CSV),
`skipped_issues` ([{issue_date, reason}]), `metrics`, `versions` (python, pandas,
numpy, lightgbm, sklearn), `duration_s`.

`metrics`: `rows` (total / missing_truth / observed / clean_targets /
excluded_as_downtime_or_gap) и две группы — `clean_targets`, `all_observed` —
каждая по турбинам и горизонтам с `n`, `mae`, `rmse`, `mae_baseline`.
В `clean_targets` дополнительно `quantile_coverage_p10_p90` — **измеренное**
эмпирическое покрытие интервала P10–P90 и `quantile_band_rows`. Номинальная
ширина 80% ≠ калиброванность: пока измеренное покрытие не равно номинальному,
интервал нельзя описывать как «калиброванные 80%».

Метрики всегда пересчитываемы из CSV: `compute_metrics(csv_path)` читает
сохранённый файл, а не память процесса.

## Отношение к канонической сдаче

Финальный артефакт сдачи по-прежнему обучается на всех целях по 2026-01-31
(`python -m src.cli train`) — после оценки это законно и правильно: чем свежее
данные, тем лучше февральский прогноз. `train_report.json` теперь содержит блок
`protocol` с ролями периодов и пометкой `metrics_measured_on: "tune"` — его числа
относятся к данным настройки. Любой оценочный результат обязан указывать
`trained_through` той модели, которая реально предсказывала.
