# Совместная работа и интеграция

Текущая схема согласована пользователем 23.09.2026: два внешних агента публикуют
свои ветки, координирующий агент делает интеграционные изменения и объединяет результат.
Требования задачи находятся в [CASE](CASE.md); этот документ описывает git-процесс.

## Ветки и handoff

| Ветка | Владелец |
| --- | --- |
| `dev/forecast-availability` | Agent 1: погодные срезы и признаки |
| `dev/evaluation-protocol` | Agent 2: обучение и проверка точной конфигурации модели |
| `dev/judge-readiness` | Интегратор: запуск, документация, UI и сборка релиза |

Точные файлы — в [TASKS](TASKS.md). Каждый исполнитель начинает от свежего `origin/main`
в отдельном worktree/клоне, сохраняет чужую незакоммиченную работу и пушит только свою ветку.
Не делать force-push, `reset --hard` или самостоятельное слияние в `main`.

В handoff нужны branch, полный SHA, база, изменённые интерфейсы, команды проверок с результатом,
открытые ограничения и команда воспроизведения. Не считать локальный коммит опубликованной веткой.
Коммиты содержат конкретное описание на русском, без AI attribution trailers.

## Кто пишет сгенерированные результаты

`forecasts/` и `models_artifacts/` — согласованные результаты команды. Их обновляет
один интегратор после проверки обеих веток. Сначала испытать объединённую версию отдельно:

```bash
python -m src.cli run-agent --start 2026-01-31 --end 2026-02-27 \
  --no-llm --output-dir runs/integration
python -m scripts.verify_submission --directory runs/integration
python -m scripts.compare_runs --a forecasts --b runs/integration
```

В `--output-dir` попадают все результаты прогона; сравнение со вчерашним выпуском читает
тот же каталог. `runs/` игнорируется git. Использовать отдельный каталог для каждой версии.
Сравнение чисел показывает расхождения, но не определяет, какая модель точнее.

Без `--output-dir` сохраняется прежний каталог `forecasts/`. Если выбран offline-режим
или ключ отсутствует, CLI защищает имеющиеся LLM-отчёты. `--overwrite` разрешает их
замену шаблоном в выбранном каталоге. Каноническое обновление должно быть осознанным действием
интегратора, а не побочным эффектом smoke-теста.

## Порядок общей сборки

1. Получить оба handoff, выполнить `git fetch origin` и проверить заявленные SHA/файлы.
2. В изолированной интеграционной ветке применить изменения признаков, затем оценки,
   затем изменения запуска/документации. Сохранить авторскую историю; конфликты разрешить
   с учётом контрактов, а не автоматическим выбором одной стороны.
3. Прогнать весь набор тестов и повторить оценку на объединённом коде. Результаты Agent 2
   до слияния Agent 1 остаются предварительными.
4. Обновить UI/цифры по сохранённым оценочным прогнозам; один раз пересчитать финальные
   модели и февральские результаты, проверить полноту и происхождение файлов.
5. Проверить чистый запуск и отсутствие секретов/временных результатов в diff. Получить
   свежий `origin/main`, включить новые командные коммиты, повторить затронутые проверки.
6. Опубликовать проверенную интеграцию обычным push в `main`. При отказе fetch-first
   подтянуть изменения и повторить интеграцию, не переписывать удалённую историю.

Рабочие промежуточные коммиты следует публиковать регулярно. Частота коммитов не заменяет
проверку совместимости перед слиянием. Если нужен откат опубликованного изменения — отдельный
revert-коммит с описанием причины, с сохранением чужой работы.
